# 发布产物与上传中继说明

本文说明 `Build Package`（`.github/workflows/build.yml`）在推送 `v*` 标签时的**发布产物命名规则**与**上传中继（Storage Relay）分发**行为。

## 一、发布产物清单

| 文件名 | 来源 | 进 GitHub Release | 上传中继 |
| --- | --- | --- | --- |
| `gsm3-management-panel-windows.zip` | Windows x64 构建产物（`dist/package/`） | ✅ | ✅ |
| `gsm3-management-panel-linux.tar.gz` | Linux x86_64 构建产物（`dist/package/`） | ✅ | ✅ |
| `gsm3-management-panel-linux-arm64.tar.gz` | Linux ARM64 构建产物（`dist/package/`） | ✅ | ❌ 不上传 |

要点：

- **文件名固定、不再追加版本号**。版本信息由 tag 承载，产物内部元数据（`APP_VERSION` 注入的版本号）不受影响。
- **只有 x86_64 的两个包会上传中继**；ARM64 等其它架构只保留在 Release 页面，供手动下载或自行取用。
- Release 与中继拿到的是**同一个文件本体**（中继 job 下载的是 `create_release` 打好包后交接的 artifact），因此两处的 SHA-256 一致。
- 同一 tag 重新发布时，同名资产会**就地覆盖**（`softprops/action-gh-release` 与中继都是覆盖语义），重跑发布不会残留旧文件。

## 二、为什么固定文件名

对外下载地址（下载站、脚本、文档）可以长期写死，例如：

```text
https://github.com/GSManagerXZ/GameServerManager/releases/latest/download/gsm3-management-panel-linux.tar.gz
https://<下载站>/开源项目/GSManager/gsm3-management-panel-linux.tar.gz
```

换版本时地址不变、内容更新，避免每次发版都要改一遍链接。代价是**旧版本归档不可再按文件名区分**，需要保留历史包时请改用 tag 对应的 Release 页面，或在中继统一路径里另带版本目录。

## 三、上传中继

### 3.1 调用方式

中继能力由独立仓库 `yxsj245/Download_Station_CICD` 提供（reusable workflow）。`build.yml` 末尾新增两个 job，各自负责一个文件：

```yaml
  relay_upload_linux:
    needs: create_release
    if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')
    uses: yxsj245/Download_Station_CICD/.github/workflows/relay-upload.yml@v1
    with:
      artifact-name: gsm3-management-panel-relay-x64
      file: gsm3-management-panel-linux.tar.gz
      logical-path: '开源项目/GSManager/gsm3-management-panel-linux.tar.gz'
    secrets:
      RELAY_ADMIN_KEY: ${{ secrets.RELAY_ADMIN_KEY }}
      RELAY_UPLOAD_KEY: ${{ secrets.RELAY_UPLOAD_KEY }}
```

- 中继 workflow 一次调用只上传一个文件，所以 Windows / Linux 各起一个 job，两者并行执行。
- 文件交接：`create_release` 打包完成后把 x86_64 的两个文件作为 artifact `gsm3-management-panel-relay-x64` 上传（保留 7 天），中继 job 通过 `artifact-name` 下载后再上传，避免各 job 重复打包导致内容不一致。
- 中继地址不从这里传：中继 workflow 会读取调用方的变量 `RELAY_BASE`（组织级 variable）。
- 中继密钥由调用方通过 `secrets:` **显式映射**传入（中继侧声明为必填）。刻意不用 `secrets: inherit`：GitHub 只允许「同一组织 / 同一企业」内使用 `inherit`，而调用方 `GSManagerXZ/GameServerManager` 与中继仓库 `yxsj245/Download_Station_CICD` 属于不同容器，只能用显式映射；将来中继仓库若迁入同一组织或企业，可改用 `secrets: inherit`。

### 3.2 统一路径

| 本地文件 | 中继统一路径 |
| --- | --- |
| `gsm3-management-panel-windows.zip` | `开源项目/GSManager/gsm3-management-panel-windows.zip` |
| `gsm3-management-panel-linux.tar.gz` | `开源项目/GSManager/gsm3-management-panel-linux.tar.gz` |

统一路径规则（中继脚本会在本地先校验，非法路径不会发起任何请求）：相对 POSIX 路径、不带首尾 `/`、末尾必须是文件名、不超过 1024 字节；禁止 `\ : * ? " < > |` 与控制字符；不允许空段、`.`、`..` 以及以空格或点结尾的路径段。查重按 ASCII 小写比较，中文路径段合法。

### 3.3 触发与执行顺序

```text
push tag v* ─┬─ build_linux(x64, arm64) ─┐
             └─ build_windows ───────────┴─> create_release ─┬─> relay_upload_linux
                                                             └─> relay_upload_windows
```

- 只有**推送 `v*` 标签**时才会走发布流程；`workflow_dispatch` 手动构建不会创建 Release，也不会调用中继。
- `create_release` 成功后才会上传中继（`needs: create_release`）；Release 创建失败或被跳过时，中继 job 一并跳过。
- 中继任务会轮询到终态（`succeeded` / `partial_failed` / `failed` / `cancelled`）才算结束，结果在运行 Summary 里可见（统一路径、task_id、SHA-256、各渠道结果）。

## 四、前置条件（重要）

调用中继前需要满足以下条件，任一条不满足都会在**任何上传发生之前**失败：

1. **中继仓库可见性**：`yxsj245/Download_Station_CICD` 保持 **public**，本仓库才能引用它的 reusable workflow。private 的个人账号仓库只能被同账号仓库引用，`GSManagerXZ` 这类组织下的仓库引用不到。
2. **调用方白名单**：中继仓库 `scripts/relay-upload.sh` 顶部的 `ALLOWED_CALLER_OWNERS` / `ALLOWED_CALLER_REPOSITORIES` 必须包含本仓库（当前已包含 `GSManagerXZ/GameServerManager`），否则守卫在 `guard` 阶段即以退出码 9 拒绝，且不会解析任何凭证、不会发起任何请求。
3. **调用方凭证**（本仓库侧配置，中继仓库不保存任何密钥）：
   - Organization secret `RELAY_ADMIN_KEY`：中继的 `SR_ADMIN_API_KEY`，登记统一路径必须用；
   - Organization secret `RELAY_UPLOAD_KEY`：中继的 `SR_UPLOAD_API_KEY`，上传正文、查询任务用；
   - Organization variable `RELAY_BASE`：中继对外地址，**不带尾斜杠**（中继 workflow 通过 `vars.RELAY_BASE` 读取）。
   两个 secret 与这个 variable 都要对 `GSManagerXZ/GameServerManager` 可见（All repositories 或指定仓库）。缺 secret 时中继 job 会因为「必填 secret 未传入」直接失败，缺 variable 时会提示「未取到中继地址」。
4. **坐标变更**：中继仓库迁移或改名后，`build.yml` 里两处 `uses:` 的仓库坐标要同步更新。

> 现状：中继仓库已改为 public 且白名单已放行本仓库，剩下的是在 `GSManagerXZ` 组织级配齐上面三个凭证。
> 在此之前中继 job 会失败，**但不会影响 Release 本身的发布**（`create_release` 是它们的前置，不会被反向影响）。

## 五、排错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `调用方未授权：… 不在本 CICD 的调用方白名单内`（退出码 9） | 白名单没有本仓库 | 在中继仓库加白名单并移动 `v1` 标签 |
| 调用中继 job 直接报「必填 secret 未传入」之类的校验错误 | 本仓库/组织没有配 `RELAY_ADMIN_KEY`、`RELAY_UPLOAD_KEY` | 在 `GSManagerXZ` 组织级补 secret，可见范围包含本仓库 |
| `未取到中继地址` | 没有配 `RELAY_BASE` variable | 配组织级 variable `RELAY_BASE`（不带尾斜杠） |
| `中继地址不是 http(s) 开头`（退出码 2） | `RELAY_BASE` 带了尾斜杠或写成了别的协议 | 改成 `https://中继域名` 形式 |
| `统一路径含有禁用字符 / 存在空段`（退出码 2） | `logical-path` 写法不合法 | 按 3.2 的规则修正，注意不要带首尾 `/` |
| 中继 job 报找不到文件 | artifact 名称或文件名不匹配 | 确认 `artifact-name: gsm3-management-panel-relay-x64` 与 `file:` 的实际文件名一致 |
| 中继 job 被跳过 | 不是标签推送，或 `create_release` 未成功 | 检查触发方式与 `create_release` 日志 |

首次接入建议把中继仓库文档里的 `dry-run: 'true'` 用法临时加进 `with:` 跑一次：只校验参数、调用权限与统一路径，不发起任何请求。
