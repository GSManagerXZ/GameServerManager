# 依赖升级说明

本文档记录本次项目依赖升级的范围、处理原则和验证方式，方便后续继续升级时快速参考。

## 升级范围

- 根目录 `package.json` / `package-lock.json`
- `client/package.json` / `client/package-lock.json`
- `server/package.json` / `server/package-lock.json`

## 处理原则

- 先升级到当前项目可稳定运行的最新兼容版本（semver `^` 范围内的 Wanted 版本）。
- 对于会引入源码破坏性变化的主版本，优先保持在兼容区间内，避免一次性把构建链和业务代码一起推翻。
- 如果某个新版本引入了类型错误或接口变更，先回退到可用版本，再根据需要逐个修复源码。
- 优先修复依赖漏洞，通过 `npm audit fix` 和 `overrides` 字段解决传递依赖的安全问题。

## 2026-10 安全修复与兼容区间升级

本轮在原有升级基础上继续收敛依赖安全风险，处理范围为根目录、`client`、`server` 三个 `package.json` / `package-lock.json`。

### 本轮原则

- 先消除 `npm audit` 报出的高危漏洞，再把三处依赖升到各自 `^` 声明范围内可用的最新版本。
- 不做大版本升级（React 19、antd 6、Tailwind 4、Vite 8、ESLint 10、Express 5、TypeScript 7 等留待后续分批推进），避免一次性推翻构建链和业务代码。
- 直接依赖的版本区间声明保持原样，只通过 `npm update` 与 `overrides` 收敛到安全版本，减少与上游分支的冲突面。
- 传递依赖漏洞优先用 `overrides` 精确覆盖到修复版本，而不是联动升级引入方。

### 既有测试问题的定位与修复

`client` 的测试在升级前就存在失败项，本轮一并定位并修复（只改测试，不动业务代码）：

- 问题：`client/src/utils/__tests__/chunkUpload.preservation.test.ts` 有 5 项失败，断言沿用 10MB 阈值、50MB 分片，而实现已在 `0fd98a9 优化分片参数`（2026-03-02）改为 20MB 阈值、20MB 分片。
- 判定依据：`属性1-边界` 直接断言 `ChunkUploader.shouldUseChunkUpload(10MB + 1) === true`，而实现是 `fileSize > 20 * 1024 * 1024`，该断言与依赖版本无关，必然失败；测试文件最后修改于 2026-02-26（`59ad7eb 优化分片上传`），早于实现改动。因此这 5 项失败是历史遗留，不是本次升级引入的回归。
- 同步修复内容：
  - `THRESHOLD` 由 `10 * MB` 改为 `20 * MB`，`DEFAULT_CHUNK_SIZE` 由 `50 * MB` 改为 `20 * MB`，并在常量处注明与 `chunkUpload.ts` 实现的对应关系，方便下次实现调整时同步。
  - 属性 2 的随机文件大小下界由 `11MB` 改为 `THRESHOLD + 1`：低于 20MB 的文件不会走分片上传，原下界会让 `waitFor` 一直等不到 `uploading` 事件而超时。
  - 属性 2、属性 2-具体、属性 5 的分片数与批次数断言改为按 `FILE_SIZE / DEFAULT_CHUNK_SIZE` 推算，不再硬编码 `4`、`6` 等旧值。
  - 属性 2 每轮都要跑完整上传与清理流程，分片粒度由 50MB 变细到 20MB 后单用例耗时升到约 48 秒，因此为该用例显式设置 120 秒超时（全局 `testTimeout` 为 30 秒）。
- `client/src/utils/__tests__/chunkUpload.fault.test.ts` 的 `upload()` 返回的 Promise 在 `cleanupUpload` 接管前可能已经 reject，全量并发运行时会触发 unhandled rejection，导致 `npm test` 即使断言全过也以退出码 1 结束。已在 3 处调用点提前挂载空的 rejection 处理器，失败仍由 `cleanupUpload` 统一忽略，不改变测试语义。

修复后 `client` 的 `npm test`：2 个测试文件、10 项测试全部通过，无 unhandled rejection，退出码 0。
